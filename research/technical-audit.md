# Technical audit and bounded proof of concept

Research date: **2026-11-12**. This appendix distinguishes documentation, source inspection, third-party issue reports, local tests, and proposed implementation. The GitHub connector was used for public repository inspection. No outside repository was installed or executed. Only the original standard-library prototype in this repository was run, with synthetic data. No account, deployment, external message, purchase, customer-data upload, or catalog write was performed.

The technical recommendation is to validate a **narrow supplier-file exception report**, with an explicit customer-approved schema and no imports, before buying an orchestration platform or building a service. General CSV checking is already available in open source and paid products. Deterministic software should do the checking. An optional AI explanation may improve readability, but must cite actual finding codes and cannot change values, invent errors, or approve a release. Demand, acquisition cost, and low owner workload remain unproven.

## Build, buy, reuse, or outsource

Costs and time below are planning assumptions unless a vendor source is linked above. They are alternatives, not additive subscriptions. They exclude acquisition and customer support, which belong in the main financial/workload model.

| Approach | Cash/setup assumption | Recurring owner maintenance assumption | Appropriate decision |
|---|---|---|---|
| Small deterministic custom supplier check | Local demonstration $0 external spend; 12–25 hours to turn a fixed schema into a supervised internal pilot, plus demand work | 15–30 minutes/week at small volume; incidents can add 2–4 laptop hours | Cheapest learning route. Keep one schema, one file size cap and no writes. The delivered demonstration is not that complete hosted pilot. |
| Reuse Frictionless | $0 root license fee; approximately 8–20 integration hours plus private hosting if needed | 20–45 minutes/week for rules, updates and dependency checks | Useful if several formats/schema rules prove necessary. Customer-specific interpretation remains work. |
| Buy established monitoring | Observed $8.99/month changedetection hosted offer; 2–5 hours setup for a small source set | 10–30 minutes/week plus page-break incidents | Prefer over self-hosting for a monitoring experiment, subject to permitted sources and account terms. Does not solve willingness to pay. |
| Self-host changedetection | Illustrative $10–30/month hosting/backups; 8–16 hours secure setup, not a vendor quote | 30–60 minutes/week baseline plus outages | Downgrade for a 60-minute total owner budget unless existing skills and infrastructure reduce measured work. Browser memory/CPU must be load-tested; no GPU needed without a local model. |
| Buy orchestration | n8n prices above; 4–12 integration hours, separate from checker work | 15–30 minutes/week for credentials and failed workflows | Unnecessary for the initial offline demand sample. A subscription can remove server patching but not broken business logic. |
| Limited contractor setup | Assumption: 10–20 hours × $35–75/hour = $350–1,500; maintenance 1–2 hours/month at same rate | Add 15–30 minutes/month owner briefing/review; incident coverage separately priced | Useful fixed deliverable after demand; not proof of autonomy or a 24/7 support promise. Ownership, secrets access and handover require a written scope. |

The single most useful retained decision is approval of the first mapping/rule set for a supplier, followed by a short weekly review of false positives. It prevents repeated explanations and false alarms. Measure whether 15 extra review minutes eliminate at least 15 minutes of customer support/rework; if not, simplify the rule or drop it. Large custom exceptions are outside the offer.

## What the local prototype establishes

[Usage and reproducible checks](../prototype/README.md), [source](../prototype/feed_preflight.py), [tests](../prototype/test_feed_preflight.py), and [sample results](../prototype/samples/) are included. Python 3.14.7 on Windows was used. Fourteen tests passed after correcting SQLite connection closure discovered by the first run. The correction matters on Windows because a transaction context does not close its connection and the first test run could not remove temporary databases. No paid APIs or unfamiliar packages were installed.

Tested: explicit required headers and values; trim-normalized, case-sensitive SKU duplicates; malformed/nonfinite/localized prices; formula-like prefixes and Unicode format controls; wrong column counts; quoted commas, quotes and newlines; UTF-8/empty/NUL/malformed CSV; file/row limits; URL shape (no fetch); JSON that omits raw malicious cells; state isolation; repeat input; quiet unchanged findings; recovery and reversion; corrupt state; refusal to overwrite input via equal paths. HTML is inert input in this implementation because it is never rendered or echoed; no claim of HTML sanitization is made.

Not established: Shopify/Google feed conformance, all ISO currencies, supplier correctness, link reachability, spreadsheet formula sanitization, price reasonableness, data loss prevention, upload authentication, concurrency at scale, restore, scheduler uptime, API/token behavior, email delivery, a phone interface, payment or owner-minute performance. A currency is only three uppercase ASCII letters, and 0 is accepted as a price. Real business rules must be agreed before use. The sample is synthetic and deliberately unsuitable for a production import.

Idempotency is limited: feed ID + rules version + file hash identifies a run. Finding signatures suppress repeat digest decisions; a changed raw value with the same finding code/row is intentionally quiet. SQLite records are transactional, but the local output files and state do not share a transaction. A write failure after committing state can suppress the next digest; a production sender must use a durable outbox, delivery acknowledgments and replay. No retry loops, delivery service or scheduler are implemented. This is explicitly a local technical feasibility demonstration, not unattended fulfillment.

## Proposed operating design after demand validation

Use a customer-owned file delivered through an agreed secure upload/export route. One scheduled worker receives a bounded file, records an immutable job ID, validates a pinned schema, and writes a structured report. Unknown schema or encoding pauses that feed. Do not execute cells, visit embedded URLs, import catalogs, change prices, or follow instructions in file content. A known clean file can be reported under preauthorized rules after supervised gates; new rules and mappings await a batch decision. Optional AI reads only redacted finding summaries and is omitted if it adds no measured benefit.

Persistent hosting and scheduling must be independent of the owner's laptop. Proposed limits: 5 MB/file, 10,000 rows, at most one daily file/customer initially, 30-day raw-file retention only if contractually needed, and a $25/month infrastructure cap for a small pilot. These are experiment boundaries, not observed costs/capacity. A worker uses unique `(customer, file hash, rule version)` keys; max three retries for transient transport failures (1, 5, 30 minutes), no automatic retry for schema failures, and dead-letter queue thereafter. A durable outbox owns notification delivery. Financial jobs are excluded. Maximum parallelism is one until timing and memory are measured. On budget breach, pause optional AI first and then new intake; preserve a visible paused status and warn that reports will be late.

Record last successful run, next expected input, oldest pending job, error reason, attempts and output version. Alert once on an actionable state transition; suppress duplicates. Weekly batch review catches a missing digest using an independent last-success record. Encrypted backup plus an actual restore trial is required before customer files; keep secrets outside the repository and restrict storage by customer. Token expiry tests only become necessary if an authorized connector is added. Critical fallback: a manual download and local check during the agreed weekly batch, or pause delivery and offer the contracted credit; never silently label stale data current.

### Phone capability boundary

[Gmail's Android help](https://support.google.com/mail/answer/6585?co=GENIE.Platform%3DAndroid&hl=en) documents opening, reading and replying to a message. Thus a simple pilot can send a concise report for phone reading and let the owner reply to customers or a human operator. An email reply does **not** itself pause a server, approve a job, retry a run or issue a refund. Those control actions require an authenticated mobile web control or a verified existing vendor control; neither has been built or phone-tested here. The owner's device/account has not been inferred. The changedetection repository contains a PWA-install dependency comment; that is evidence of intended phone use, not tested usability or an independently verified native app.

Avoid a custom dashboard for the first three-file/manual pilot. The owner can read findings and send a constrained response using existing email; laptop execution happens in the planned batch. If demand succeeds and hosted routines begin, implement and test only pause-feed, retry-safe-job, acknowledge/reject and download-report controls. One phone walkthrough estimate: open digest (1 tap), read 6 lines (45 seconds), open one exception (1 tap), review a safe preview (60–120 seconds), choose action and confirm (2 taps, 20 seconds), record time (10 seconds): about 2–4 minutes per exception. These are estimates, not measured UI outcomes; count all of them in weekly owner time.

| Absence | Proposed behavior and cost |
|---|---|
| Missed check-in | Previously authorized schema checks continue; novel rules wait. No new commitment is approved. Next batch absorbs queue time. |
| 10-hour workday absence | Fits a weekly/nonurgent report promise. Transient failures exhaust bounded retries and park; report shows stale/failed status. Exclude same-day inventory or ad-spend protection promises. |
| 48-hour absence | Existing checks may continue within quota; intake requiring new mapping pauses. Customer receives previously authorized status notice only if such notice policy was agreed. Revenue/retention can suffer; pausing is not continuous fulfillment. |
| Week of minimal supervision | Stop new onboarding and optional changes. A scheduled check may run under fixed rules, but recurring paid delivery should pause if its review gate is not met. Reserve credits/refunds and expect 1–3 hours of batch/laptop recovery, an assumption to measure. |

A future phone digest should show **actual** receipts/refunds/cash from reconciled payment records separately from estimated accrued revenue/cost/margin, customer count, last success, queue age, failures, owner minutes, pending decisions and the next deadline. The current prototype correctly labels those financial/time fields unmeasured. Silence is never approval. If basic customer expectations require workday response, reject that service scope rather than hiding support in a bot.

## Decisive rechecks and remaining cheap tests

1. Reopened exact repository licenses, releases, issue bodies, code and configuration. Result: permissive core candidates exist; n8n and unclear-license CSV competitors cannot be casually described as open source for resale.
2. Challenged raw-monitoring value using the $8.99 hosted substitute. Result: general alert resale has weak differentiation; require a specific expensive decision the buyer cannot already solve cheaply.
3. Challenged library confidence with current issues and inspected logic. Result: release activity and test counts do not remove regressions. Freeze a version and use customer-shaped regression fixtures.
4. Ran local tests, recorded the initial connection-lifecycle failure and fix, then reran. Result: bounded CSV behavior works on synthetic inputs, not proof of production reliability or market demand.
5. Checked a real mobile email capability. Result: read/reply exists; server controls remain a build-and-device-test gate. No phone workload claim is validated.
6. Cheapest next technical check after consent: 20 anonymized supplier files across at least three dates, compare findings to a human-labeled gold set and to the customer's present process. Predeclare zero critical false-negative tolerance in this small sample, <=5% irrelevant findings, and <=5 minutes review/file. This cannot estimate rare error rates; retain human review while accumulating evidence. Demand/payment tests must precede hosted development.

Access gaps: no repository runtime tests, dependency-wide security/license audit, video/transcript inspection for this technical appendix, hardware load test, app-store check, hosted browser/phone workflow, live supplier/export data, actual payment, integration permissions, reseller clearance or production incident history. No code or infrastructure was deployed. These gaps remain explicit gates, not successful checks.
